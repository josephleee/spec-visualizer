# 문서별 파싱 규칙

상태: 구현 기준 문서 (2026-11-18). "지금"은 `server/parsers.ts`가 이미 하는 일, "추가"는 새 화면(줌 캔버스)을 위해 이번에 넣는 규칙입니다.

## 공통 원칙

1. **내용을 버리지 않는다.** 규칙에 맞지 않는 부분은 `raw` 블록(원문 마크다운)이나 각 블록의 `rest`로 남겨 화면에 그대로 보여 준다. 숨기는 것은 HTML 주석뿐이다.
2. **파일 순서를 지킨다.** 블록은 문서에 나온 순서대로 나온다.
3. **파서가 실패해도 문서는 보인다.** 예외가 나면 문서 전체를 `raw` 블록 하나로 돌려준다.
4. **숫자는 문서에 적힌 요약이 아니라 직접 센 값을 쓴다.** 예: `tasks.md`의 Summary가 "65개 중 50개"라고 적혀 있어도 체크박스를 세어 66개 중 51개로 표시한다.
5. **문서의 글은 신뢰하지 않는다.** 이미지와 스크립트는 실행하지 않고 글자로만 보여 준다.

모든 문서에 먼저 적용되는 전처리:

| 단계 | 규칙 |
|---|---|
| 정리 | BOM 제거, CRLF를 LF로, HTML 주석 제거(코드 블록 안의 주석은 유지) |
| 제목 | 첫 `#` 제목이 문서 제목 |
| 머리 정보 | 첫 `##` 앞의 `**이름**: 값` 줄들이 `meta` (예: Feature Branch, Created, Status) |
| 구획 | `##` 단위로 나누고, 문서 종류별 규칙을 적용 |

## 파일을 문서 종류로 나누는 규칙

| 경로 | 종류 | 단계 |
|---|---|---|
| `.specify/memory/constitution.md` | constitution | 1 헌법 |
| `specs/<기능>/spec.md` | spec | 2 명세 |
| `specs/<기능>/plan.md` | plan | 3 계획 (대표 문서) |
| `specs/<기능>/research.md`, `data-model.md`, `quickstart.md`, `contracts/*` | research, data-model, quickstart, contract | 3 계획 (딸린 문서) |
| `specs/<기능>/tasks.md` | tasks | 4 작업 분해, 5 구현 |
| `specs/<기능>/checklists/*.md` | checklist | 6 완료 |
| 그 밖의 `.md` | other | 단계 없음, 기능 문서 목록에만 표시 |

기능의 단계는 파일로 정한다: 작업이 모두 끝남 → 완료, 끝난 작업이 하나라도 있음 → 구현, `tasks.md` 있음 → 작업 분해, `plan.md` 있음 → 계획, 그 외 → 명세.

## 프로젝트 (헌법과 README)

| 읽는 것 | 지금 | 추가 |
|---|---|---|
| 프로젝트 이름 | 폴더 이름 | |
| 한 줄 소개 | 없음 | `README.md`의 첫 문단(제목, 배지, 이미지 줄을 건너뛴 첫 글 문단). 없으면 표시하지 않는다 |
| 헌법 버전 | `**Version**: x` | `**Ratified**`, `**Last Amended**`도 함께 |
| 원칙 목록 | 문서 블록 안에만 있음 | 원칙 제목 목록을 프로젝트 정보에도 실어 홈의 헌법 카드에 표시 |

## 1. constitution.md → 원칙 판

| 표시 | 규칙 | 화면 |
|---|---|---|
| `## Core Principles` 아래 `###` | 원칙 하나가 카드 하나 (`cards`) | 번호가 붙은 원칙 판 |
| 그 밖의 `##` 중 `**이름**: 값`이 있는 구획 | `fields` | 항목표 |
| 맨 아래 `**Version** \| **Ratified** \| **Last Amended**` | `fields`의 세 항목 | 큰 숫자 세 개 |
| 나머지 | `raw` | 원문 |

## 2. spec.md → 스토리와 시나리오 흐름

| 표시 | 규칙 | 화면 |
|---|---|---|
| `### User Story N - 제목 (Priority: P1)` | 스토리 (`stories`), 우선순위 포함 | 스토리 상자, 우선순위 표 |
| `**Why this priority**`, `**Independent Test**` | 스토리의 `why`, `test` | 스토리 왼쪽 칸 |
| `**Acceptance Scenarios**` 목록의 `**Given** … **When** … **Then** …` | 시나리오 (`given`, `when`, `then`) | 조건 → 행동 → 결과 세 칸 흐름 |
| `- **FR-001**: …`, `- **SC-001**: …` 같은 목록 | ID 목록 (`idList`), `###`이나 `####` 제목별로 묶음 | 묶음별 개수 막대와 항목, 성공 기준 격자 |
| `[NEEDS CLARIFICATION: …]` | 개수를 세어 기능의 "열린 질문"으로 | 홈 카드에 표시 |
| Edge Cases, Key Entities 등 나머지 | `raw` | 원문 |

**추가: 두 번째 스토리 쓰기 방식.** 실제 프로젝트(hl)의 명세 9개 중 6개는 위 형식이 아니라 아래 형식이라, 지금은 전부 원문으로만 나온다.

```markdown
### US-1: Basic Multi-File Concatenation
**As a** DevOps engineer
**I want to** process multiple log files in a single command
**So that** I can view logs in one stream

**Acceptance Criteria:**
- Given multiple log files
- When I run `hl file1.log file2.log`
- Then all logs are displayed
- And the order is preserved
```

| 표시 | 규칙 |
|---|---|
| `### US-N: 제목` | 스토리. 우선순위는 없음 |
| `**As a** / **I want to** / **So that**` | 스토리의 `narrative` (새 항목) |
| `**Acceptance Criteria:**` 아래 목록 | `Given`으로 시작하는 줄에서 새 시나리오를 시작하고, `When`, `Then` 줄을 채운다. `And`, `But` 줄은 바로 앞 칸에 이어 붙인다 |
| Given/When/Then으로 시작하지 않는 줄 | 스토리의 `rest`에 남긴다 |

## 3. plan.md → 기술 명세표와 딸린 문서

| 표시 | 규칙 | 화면 |
|---|---|---|
| `## Technical Context`의 `**이름**: 값` | `fields` | 기술 명세표 |
| `## Constitution Check`, `## Project Structure` 등 | `raw` | 표는 표로, 코드 블록(폴더 구조)은 코드로 그린다 |
| 나머지 | `raw` | 원문 |

### research.md → 결정 대 대안

| 표시 | 규칙 | 화면 |
|---|---|---|
| `**Decision**`이 있는 `##` 또는 `###` 구획 | 결정 하나 (`decisions`): Decision, Rationale, Alternatives considered | 왼쪽에 결정과 이유, 오른쪽에 버린 대안 |
| `Decision`이 없는 구획 | `raw` | 원문 |

대안이 적혀 있지 않은 결정은 "대안 기록 없음"으로 표시한다(실제 문서 11개 중 9개가 그렇다).

### data-model.md → 엔티티 카드

| 표시 | 규칙 | 화면 |
|---|---|---|
| `## Entities` 아래 `###` | 엔티티 하나가 카드 하나 (`cards`), 내용은 마크다운 | 엔티티 카드. 카드 안의 표와 코드는 그대로 그린다 |
| Relationships, State Transitions 등 | `raw` | 원문 |

엔티티의 필드를 코드에서 뽑아내지는 않는다. 언어마다 달라서 틀리기 쉽다.

### quickstart.md → 순서 있는 단계

전용 파서 없이 `##` 구획이 그대로 `raw` 블록이 된다. 화면에서는 구획마다 번호를 붙인 단계로 그리고, 코드 블록은 코드로 보여 준다.

### contracts/* → 원문 코드

`.md`가 아닌 파일은 코드 블록 하나(`code`)로, 확장자를 언어로 삼는다.

## 4·5. tasks.md → 작업 칸과 진행률

| 표시 | 규칙 | 화면 |
|---|---|---|
| `## Phase N: …` (체크박스가 있는 `##`) | 단계 (`phase`) | 단계 줄 |
| `- [ ]`, `- [x]` | 작업 하나: 끝남 여부 | 칸 하나 (채움 = 끝남) |
| `T001` (`T006a` 같은 접미 글자 허용) | 작업 ID | 칸의 글자 |
| `[P]` | 병렬 가능 | 같은 열에 쌓아 그림 |
| `[US1]` | 스토리 꼬리표 | 스토리별 진행 막대 |
| 단계 안의 `**Goal**:`, `**Purpose**:` 등 | 단계의 `fields` | 단계 설명 |
| 체크박스가 없는 `##` | `raw` | 원문 |
| 체크박스 목록 사이의 글, 하위 제목 | 단계의 `rest` | 원문 |

같은 문서를 두 단계에서 다르게 보여 준다.

- **4 작업 분해:** 구조. 단계가 몇 개이고, 어떤 작업이 병렬이며, 어느 스토리에 속하는가.
- **5 구현:** 진행. 전체 몇 개 중 몇 개가 끝났고, 단계별·스토리별로 무엇이 남았으며, 다음 명령은 무엇인가.

**추가: 값 끝의 구분선 제거.** 지금은 `**Purpose**: …` 값 끝에 문서의 `---` 구분선이 딸려 들어온다. 값에서 떼어 낸다.

단계 제목의 완료 표시 이모지(예: ✅)는 화면 제목에서만 뺀다. 끝남 여부는 칸이 보여 주기 때문이다.

## 6. checklists/*.md → 확인 목록

`tasks.md`와 같은 규칙으로 읽는다. `##`이 묶음, 체크박스가 항목이다. 화면에는 묶음별 확인 개수와 항목을 그린다. 체크리스트가 여러 개면 문서 상단에서 고른다.

## 종류를 모르는 `.md`

`##` 구획이 그대로 `raw` 블록이 된다. 기능의 문서 목록에 "기타"로 나오고, 원문 마크다운으로 보여 준다.

## 이번에 넣는 파서 변경 요약

| # | 변경 | 이유 |
|---|---|---|
| 1 | 명세의 두 번째 스토리 방식(`US-N:` 제목, As a / I want / So that, Given / When / Then 목록) | 실제 명세 9개 중 6개가 이 방식이라 지금은 그림이 안 그려진다 |
| 2 | 이름표 값 끝의 `---` 제거 | 단계 설명에 구분선 글자가 섞여 나온다 |
| 3 | 프로젝트 정보에 README 첫 문단, 헌법 비준일·개정일, 원칙 제목 목록 추가 | 홈에서 "어떤 프로젝트인지"를 보여 주려면 필요하다 |

그 밖의 새 화면 요소(단계별 개수, 스토리별 진행, 명령 안내, 표와 폴더 구조 그리기)는 파서를 바꾸지 않고 지금 블록에서 화면 쪽이 계산한다.
