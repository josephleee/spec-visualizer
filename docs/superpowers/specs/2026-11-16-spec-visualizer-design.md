# spec-visualizer 설계

작성일: 2026-11-16 · 상태: 결정 12개 확정 (2026-11-17)

## 의도

spec-kit으로 작업하는 사람이 스펙 문서를 글로 읽지 않고 화면으로 파악하게 한다.
기존 뷰어들은 모든 문서를 "마크다운 렌더링 + 체크박스 집계"로 똑같이 다룬다.
이 도구는 문서 종류마다 그 문서에 맞는 화면을 준다.

쓰는 순간은 세 가지다.

1. 작업 중간에 지금 어느 단계인지 확인할 때
2. 새로 생긴 스펙 문서를 글 대신 화면으로 보고 싶을 때
3. 갱신된 문서를 다시 볼 때

성공 기준은 두 가지다.

- 홈 화면을 보고 현재 단계와 문서 현황(개수 등)을 파악한다.
- 문서 페이지를 보고 내용을 포인트별로 이해한다.

사용자는 spec-kit 프로젝트에서 작업하는 본인 또는 팀원이며, 자기 컴퓨터에서 연다.

## 목표

- spec-kit 프로젝트 폴더에서 명령 하나로 로컬 대시보드를 띄운다.
- 홈 화면에서 기능별 단계, 문서 유무, 태스크 진행률, 미해결 질문 수를 보여준다.
- 문서 종류별 전용 화면을 제공한다.
- 파일이 바뀌면 화면이 새로고침 없이 갱신된다.
- 새 문서와 갱신된 문서를 홈에서 표시한다.
- 보기에 아름답다. 일반 마크다운 뷰어처럼 보이지 않는다.

## 하지 않는 것

- 문서 편집, 체크박스 토글 등 파일 쓰기 일체
- 갱신된 문서에서 바뀐 부분만 강조하기 (나중에 추가할 수 있음)
- OpenSpec, Kiro 등 다른 포맷
- 여러 프로젝트를 한 화면에 모으기
- AI로 페이지 생성하기
- 정적 HTML 내보내기, 호스팅, 로그인
- data-model의 엔티티 관계를 그래프로 그리기 (첫 버전은 엔티티 카드까지)

## 실패로 보는 것

- 문서 내용이 화면에서 조용히 빠진다. 인식하지 못한 부분도 반드시 보여야 한다.
- 화면이 파일보다 낡은 내용을 보여준다.
- 문서가 템플릿에서 조금 벗어났다고 페이지가 깨지거나 비어 보인다.

## 제약

- 읽기 전용이다. 프로젝트 파일을 절대 수정하지 않는다.
- 서버는 `127.0.0.1`에만 바인딩한다.
- 파일 접근은 프로젝트 루트 안으로 제한한다. 경로 탈출 요청은 거부한다.
- 마크다운 안의 원시 HTML은 렌더링하지 않는다. 문서는 AI가 쓴 것이라 신뢰하지 않는다.

## 검토한 방법

| 방법 | 내용 | 장단점 |
|---|---|---|
| 1. 규칙 기반 로컬 웹앱 (선택) | 문서의 일정한 표식을 규칙으로 읽어 전용 화면에 표시 | 즉시 뜨고 항상 최신이며 비용이 없다. 템플릿에서 벗어난 부분은 일반 마크다운으로 보인다. |
| 2. AI가 문서마다 페이지 생성 | Claude Code 스킬이 문서를 읽고 HTML 생성 | 자유 형식 문서에 강하다. 느리고 토큰이 들며, 문서가 바뀌면 낡은 화면이 남는다. |
| 3. VS Code 확장 | 방법 1을 에디터 패널로 | 터미널 중심 작업 방식과 맞지 않는다. |

사용자가 방법 1을 골랐다. "진행 확인"과 "갱신된 문서 보기"는 항상 최신이어야 하는데 방법 1만 이를 충족한다.

## 사용자가 정한 것

- spec-kit 문서를 기준으로 한다.
- 갱신된 문서는 최신 상태만 보여주고, 홈에서 갱신 표시만 단다.
- 규칙 기반 로컬 웹앱으로 만든다.
- 디자인은 hallmark / unslop 스킬로 끌어올린다.

계획 페이지(`docs/superpowers/plans/spec-visualizer-plan.html`)의 결정 12개에 대한 답 (2026-11-17):

- 화면 라벨은 영어와 한국어를 모두 지원하고 전환 버튼을 둔다. (추천안에서 바꾼 유일한 항목)
- 포트가 사용 중이면 안내를 출력하고 멈춘다.
- 미해결 질문이 있어도 `plan.md`가 있으면 Plan 단계다. 질문 수를 옆에 표시한다.
- 현재 기능은 git 브랜치 이름과 같은 기능 폴더다.
- 일부 구역만 인식되면 아는 구역은 카드, 나머지는 마크다운으로 보여준다.
- HTML 주석은 숨긴다.
- 첫 버전의 data-model은 카드만 보여준다.
- 모르는 이름의 파일은 마크다운으로 보여주고 "other"로 센다.
- 열어둔 페이지는 파일이 바뀌면 바로 갱신하고 스크롤 위치를 지킨다.
- 열람 기록은 브라우저에 저장한다.
- 프로젝트를 처음 열 때는 표시가 없다.
- 문서 변경은 내용 해시로 판단한다.

## 설계 (아래는 작성자의 판단이며 사용자가 고칠 수 있다)

### 실행

```
spec-visualizer [프로젝트 경로] [--port 4321]
```

경로를 생략하면 현재 폴더를 쓴다. 시작하면 주소를 출력한다.
`specs/` 폴더도 `.specify/` 폴더도 없으면 spec-kit 프로젝트가 아니라고 알리고 종료한다.

### 구성

- **서버 (Node, TypeScript)**: 프로젝트를 읽어 구조화된 JSON으로 만든다. 화면 파일을 서빙한다. 파일 변경을 감시해 브라우저에 알린다(SSE).
- **화면 (React, Vite)**: JSON을 받아 그린다. 변경 알림을 받으면 다시 가져온다.
- 파싱은 서버에서만 한다. 화면은 파싱하지 않는다.
- 마크다운 파싱은 `remark`(mdast)를 쓴다. 정규식으로 문서 전체를 훑지 않는다.

### 읽는 파일

| 위치 | 종류 |
|---|---|
| `.specify/memory/constitution.md` | constitution |
| `specs/<기능>/spec.md` | spec |
| `specs/<기능>/plan.md` | plan |
| `specs/<기능>/tasks.md` | tasks |
| `specs/<기능>/research.md` | research |
| `specs/<기능>/data-model.md` | data-model |
| `specs/<기능>/quickstart.md` | quickstart |
| `specs/<기능>/checklists/*.md` | checklist |
| `specs/<기능>/contracts/*` | contract |
| `specs/<기능>/` 안의 그 밖의 `.md` | other (다듬은 마크다운으로 보여주고 집계에 "other"로 넣는다) |

`specs/` 바로 아래 폴더 하나가 기능 하나다. 폴더 이름의 앞 숫자로 정렬한다.

### 내용을 잃지 않는 규칙

모든 파서는 같은 방식으로 동작한다. 문서를 제목 단위 구역으로 나누고, 아는 구역은 구조화하고, 모르는 구역은 원문 마크다운 그대로 순서를 지켜 넘긴다. 화면은 모르는 구역을 다듬은 마크다운으로 제자리에 그린다. 아는 구역 안에서 형식이 맞지 않는 항목도 같은 방식으로 원문을 보여준다.

예외는 HTML 주석(`<!-- … -->`) 하나다. spec-kit 템플릿의 작성 지침이 주석으로 남는 경우가 많고 문서 내용이 아니므로 표시하지 않는다. 그 밖의 원시 HTML은 실행하지 않고 글자 그대로 보여준다.

### 세는 규칙

- 체크박스 항목은 ID가 없어도 센다. `- [ ] T001 …`과 `- [ ] 설명만 있는 항목`을 모두 항목 하나로 본다. ID, `[P]`, `[US1]`은 있으면 읽는 선택 표식이다. spec-kit이 기능마다 만드는 `checklists/requirements.md`에는 ID가 없다.
- 미해결 질문은 `spec.md`와 `plan.md`에 나오는 `NEEDS CLARIFICATION`의 개수다. 대괄호가 있든 없든 센다.

### 문서별 화면

| 종류 | 읽는 표식 | 화면 |
|---|---|---|
| spec | `### User Story N - 제목 (Priority: P1)`, `**Why this priority**`, `**Independent Test**`, `**Given** … **When** … **Then** …`, `**FR-001**:`, `**SC-001**:`, `### Edge Cases`, `### Key Entities`, `## Assumptions`, `[NEEDS CLARIFICATION: …]` | 우선순위별 스토리 카드, 스토리 안의 Given/When/Then 시나리오, 요구사항 목록, 성공 기준 목록, 미해결 질문 강조 |
| tasks | `## Phase N: 제목`, `- [ ] T001 [P] [US1] 설명`, `**Purpose**`, `**Goal**`, `**Checkpoint**` | 단계별 흐름과 단계별 진행률, 병렬 가능 표시, 스토리별 묶음 |
| plan | `## Summary`, `## Technical Context`의 `**항목**: 값`, `## Constitution Check`, `## Project Structure`, `## Complexity Tracking` | 요약, 기술 스택 항목 표, 구조 트리, 헌법 점검 결과 |
| constitution | `## Core Principles` 아래 `###` 제목들, 그 밖의 `##` 구역, `**Version** … **Ratified** … **Last Amended**` | 원칙 카드, 버전 정보 |
| checklist | `## 범주`, `- [ ] CHK001 설명` | 범주별 점검 항목과 완료율 |
| research | `###` 주제 아래 `**Decision**`, `**Rationale**`, `**Alternatives Considered**` | 결정 카드(결정 / 근거 / 대안) |
| data-model | `## Entities` 아래 `###` 엔티티 제목, 그 안의 필드 표나 목록 | 엔티티 카드 |
| quickstart | 없음 | 다듬은 마크다운 |
| contract | 없음 | `.md`는 다듬은 마크다운, 그 외는 코드 보기 |

### 단계 판정

기능마다 다음 중 하나로 정한다. 아래로 갈수록 우선한다.

1. Specify: `spec.md`가 있다
2. Plan: `plan.md`가 있다
3. Tasks: `tasks.md`가 있다
4. Implement: 체크된 태스크가 하나 이상 있다
5. Done: 태스크가 모두 체크됐다

### 홈 화면

- 프로젝트 요약: 기능 수, 종류별 문서 수, 전체 태스크 완료/전체, 미해결 질문 수, constitution 유무와 버전
- 기능 목록: 기능마다 단계 표시(5단계 중 현재 위치), 있는 문서와 없는 문서, 태스크 진행률, 미해결 질문 수, 새 문서/갱신 표시
- 문서를 누르면 문서 페이지로 간다.
- 현재 작업 중인 기능을 맨 위에 올리고 강조한다. 현재 git 브랜치 이름과 같은 기능 폴더를 현재 기능으로 본다(spec-kit은 기능마다 같은 이름의 브랜치를 만든다). 브랜치 이름은 `git rev-parse --abbrev-ref HEAD`로 읽는다(git worktree에는 `.git/HEAD` 파일이 없다). 일치하는 폴더가 없거나 git 저장소가 아니면 강조 없이 번호순으로 보여준다.

### 새 문서 / 갱신 표시

브라우저에 문서별 "마지막으로 열었을 때의 내용 해시"를 저장한다(localStorage). 한 번도 열지 않은 문서는 "새 문서", 저장한 해시와 현재 해시가 다른 문서는 "갱신됨"으로 표시한다. 문서를 열면 표시가 사라진다. 파일 수정 시각은 쓰지 않는다. 브랜치를 바꾸면 내용이 같아도 시각이 바뀌기 때문이다.

저장은 프로젝트 절대 경로별로 나눈다. 어떤 프로젝트를 이 브라우저에서 처음 열 때는 그 시점의 문서를 모두 "이미 본 것"으로 기록한다. 그러지 않으면 기존 프로젝트의 문서 전체에 "새 문서"가 붙는다. 포트를 바꾸면 브라우저가 다른 사이트로 취급해 기록이 초기화되는데, 이는 받아들인다.

### 화면 언어

화면 라벨은 영어와 한국어 두 벌을 둔다. 화면에 전환 버튼이 있고, 고른 언어는 브라우저에 저장한다. 처음에는 브라우저 언어가 한국어면 한국어, 아니면 영어로 시작한다. 번역하는 것은 도구의 라벨뿐이다. 문서에서 읽은 내용은 원문 그대로 보여준다. 번역 라이브러리는 쓰지 않고 라벨 표 하나로 처리한다.

### 오류 처리

- 파일을 읽지 못하면 그 문서만 오류 상태로 표시하고 나머지는 정상 표시한다.
- 서버 연결이 끊기면 화면에 끊겼다고 알리고 자동으로 다시 연결한다.
- 지정한 포트가 사용 중이면 알리고 종료한다.

### 검증

- 파서마다 단위 테스트를 둔다. 템플릿 형태의 샘플과, 템플릿에서 벗어난 샘플(표식 누락, 순서 바뀜, 모르는 구역 추가)을 쓴다.
- "내용을 잃지 않는 규칙"을 테스트로 확인한다. 모르는 구역이 결과에 원문으로 남아 있어야 한다.
- 단계 판정과 경로 탈출 거부를 테스트한다.
- 공개된 실제 spec-kit 프로젝트 하나로 수동 확인한다. 샘플 파일은 직접 작성하고 남의 저장소 파일을 복사해 넣지 않는다.

## 만드는 사람에게 맡기는 것

- 화면의 모양 전부. hallmark 스킬로 방향을 잡는다. 밝은 테마와 어두운 테마를 모두 지원한다.
- JSON의 정확한 형태, 컴포넌트 구조, 폴더 구조
- 테스트 도구 선택
- npm 배포 여부와 패키지 이름
