# spec-visualizer 설계

이 문서는 spec-visualizer가 지금 어떻게 만들어져 있는지 설명한다. 프로젝트에 새로 들어온 사람이 코드를 읽기 전에 보는 문서다. 문서별 파싱 규칙은 [parsing-rules.md](parsing-rules.md)에 따로 있다.

## 목적

spec-kit(Spec-Driven Development)으로 작업하는 사람이 스펙 문서를 글로 읽지 않고 화면으로 파악하게 한다. 문서 종류마다 그 문서에 맞는 화면을 준다. OpenSpec과 Kiro로 쓴 프로젝트도 같은 화면에서 그 형식의 단계와 명령으로 보여 준다([다른 형식](#다른-형식)).

쓰는 순간은 세 가지다.

1. 작업 중간에 어느 기능이 어느 단계에 있는지 확인할 때
2. 새로 생긴 스펙 문서를 화면으로 보고 싶을 때
3. 갱신된 문서를 다시 볼 때

사용자는 spec-kit, OpenSpec, Kiro 프로젝트에서 작업하는 본인이나 팀원이고, 자기 컴퓨터에서 연다.

### 성공 기준

- 보드를 보고 기능별 단계, 문서 현황, 다음에 입력할 명령을 안다.
- 문서 페이지를 보고 내용을 항목별로 이해한다.

### 실패로 보는 것

- 문서 내용이 화면에서 조용히 빠진다.
- 화면이 파일보다 낡은 내용을 보여 준다.
- 문서가 템플릿에서 조금 벗어났다고 페이지가 깨지거나 비어 보인다.

### 하지 않는 것

- 문서 편집, 체크박스 토글 등 파일 쓰기 일체
- 갱신된 문서에서 바뀐 부분만 강조하기
- spec-kit, OpenSpec, Kiro 밖의 형식 읽기, 여러 형식을 한 화면에 보기
- 여러 프로젝트를 한 화면에 모으기
- AI로 페이지 생성하기
- 정적 HTML 내보내기, 호스팅, 로그인
- 엔티티 관계를 그래프로 그리기

## 여섯 단계

보드와 문서 페이지는 모두 단계를 기준으로 한다. 이 절은 spec-kit의 여섯 단계를 설명한다. OpenSpec과 Kiro의 단계는 [다른 형식](#다른-형식)에 있다.

| # | 단계 | 명령 | 읽는 문서 |
|---|---|---|---|
| 1 | 헌법 (constitution) | `/speckit.constitution` | `.specify/memory/constitution.md` |
| 2 | 명세 (specify) | `/speckit.specify` | `spec.md` |
| 3 | 계획 (plan) | `/speckit.plan` | `plan.md`, `research.md`, `data-model.md`, `quickstart.md`, `contracts/*` |
| 4 | 작업 분해 (tasks) | `/speckit.tasks` | `tasks.md` (구조) |
| 5 | 구현 (implement) | `/speckit.implement` | `tasks.md` (진행) |
| 6 | 완료 (done) | 없음 | `checklists/*.md` |

헌법은 프로젝트에 하나이고 기능에 속하지 않는다. 기능은 2~6단계 가운데 한 곳에 서 있다.

### 기능의 단계를 정하는 규칙

`specs/` 바로 아래 폴더 하나가 기능 하나다. 단계는 파일에서만 정한다(`server/scan.ts`의 `stageOf`). 위에서부터 먼저 맞는 것을 쓴다.

| 조건 | 단계 |
|---|---|
| `tasks.md`의 작업이 하나 이상이고 모두 체크됨 | 완료 |
| 체크된 작업이 하나 이상 | 구현 |
| `tasks.md`가 있음 | 작업 분해 |
| `plan.md`가 있음 | 계획 |
| 그 외 | 명세 |

열린 질문(`NEEDS CLARIFICATION`)은 단계를 막지 않는다. 개수만 센다.

### 기능의 순서와 현재 기능

- 폴더 이름 앞의 숫자순으로 늘어놓는다. 숫자가 없는 폴더는 뒤로 간다.
- 현재 git 브랜치 이름과 같은 폴더가 현재 기능이고 맨 앞에 온다. 브랜치는 `git rev-parse --abbrev-ref HEAD`로 읽는다. 맞는 폴더가 없거나 git 저장소가 아니면 현재 기능은 없다.

## 다른 형식

서버는 시작할 때 프로젝트의 형식을 한 번 정하고, 그동안 바꾸지 않는다. 설계 전체는 [design-formats.md](design-formats.md)(영어), 형식 조사는 [formats.md](formats.md)(영어)에 있다.

| 형식 | 알아보는 폴더 | 첫 단계 (프로젝트 문서) | 작업 단위 | 단계 |
|---|---|---|---|---|
| spec-kit | `specs/` 또는 `.specify/` | 헌법 | 기능 (`specs/<기능>/`) | 헌법, 명세, 계획, 작업 분해, 구현, 완료 |
| OpenSpec | `openspec/` | 스펙: `openspec/specs/**/spec.md`, `config.yaml`, `project.md` | 변경 (`openspec/changes/<이름>/`, 보관된 것은 `archive/<날짜>-<이름>`) | 스펙, 제안, 설계, 작업 분해, 적용, 보관 |
| Kiro | `.kiro/specs/` 또는 `.kiro/steering/` | 스티어링: `.kiro/steering/**/*.md` | 스펙 (`.kiro/specs/<이름>/`) | 스티어링, 요구사항, 설계, 작업 분해, 구현, 완료 |

- 폴더가 여러 형식에 맞으면 spec-kit, OpenSpec, Kiro 순으로 고른다. 전에 spec-kit으로 열리던 폴더는 그대로 spec-kit으로 열린다. CLI는 고르지 않은 형식과 `--format` 옵션을 알려 준다.
- 서버 쪽은 형식마다 어댑터 하나다(`server/formats.ts`). 어댑터는 알아보는 규칙, 감시할 폴더, 스캔, 문서 종류별 파서를 준다. spec-kit 어댑터는 원래의 `scanProject`와 파서 표를 그대로 쓴다.
- `Project`에는 `format`(OpenSpec, Kiro일 때만)과 `shared`(헌법 밖의 프로젝트 문서)가 붙는다. spec-kit에서는 둘 다 없으므로 JSON이 그대로다.
- 화면 쪽은 형식마다 흐름 하나다(`web/flows.ts`). 단계 목록과 문서 종류, 명령, 작업 단위를 부르는 말을 담는다. spec-kit 흐름은 원래 화면이 가정하던 값 그대로다.
- 화면 라벨의 "기능"은 OpenSpec에서 "변경", Kiro에서 "스펙"으로 바꿔 보여 준다. 셋 다 받침으로 끝나 조사가 그대로 맞는다.
- `index.html`을 줄 때 `<html data-format="…">`을 붙여, 화면이 프로젝트를 받기 전에도 맞는 단계 이름으로 뼈대를 그린다.

## 구조

```text
프로젝트 폴더 ──스캔──▶ Project JSON   (/api/project)
              ──파싱──▶ ParsedDoc JSON (/api/doc?path=…)
              ──감시──▶ changed 이벤트 (/api/events, SSE)
                              │
                              ▼
                       브라우저 (React): 보드, 단계 문서 페이지
```

| 부분 | 위치 | 하는 일 |
|---|---|---|
| CLI | `server/cli.ts`, `server/main.ts` | 인자를 읽고, 형식을 정하고, 서버를 띄우고, 주소를 출력하고, 브라우저를 연다 |
| 형식 | `server/formats.ts` | 형식별 어댑터와 형식 찾기 |
| 스캔 | `server/scan.ts`, `server/openspec.ts`, `server/kiro.ts` | 프로젝트를 훑어 기능, 문서 목록, 단계, 작업 수, 열린 질문 수, 헌법 값, README 소개를 만든다 |
| 파서 | `server/md.ts`, `server/parsers.ts`, `server/items.ts`, `server/openspec.ts`, `server/kiro.ts` | 문서 하나를 종류별 블록으로 만든다 |
| 서버 | `server/server.ts` | JSON과 화면 파일을 주고, 파일 변경을 알린다 |
| 화면 | `web/` | JSON을 받아 그린다. 형식별 단계와 명령은 `web/flows.ts`에 있다. 마크다운 문서의 구조는 서버만 읽는다 |

서버와 화면이 주고받는 형태는 `server/types.ts` 하나에 있고, 화면이 그대로 가져다 쓴다.

### 서버 경로

| 경로 | 응답 |
|---|---|
| `GET /api/project` | 요청마다 새로 스캔한 `Project` |
| `GET /api/doc?path=<경로>` | 그 문서의 `ParsedDoc`. 스캔이 찾은 문서의 경로가 아니면 404 |
| `GET /api/events` | SSE. 파일이 바뀌면 `changed` 이벤트 |
| 그 밖의 `GET` | `dist/web`의 화면 파일. 없으면 404 |

### 실시간 갱신

- 서버는 형식의 폴더(spec-kit은 `specs/`와 `.specify/`, OpenSpec은 `openspec/`, Kiro는 `.kiro/`)를 하위 폴더까지 감시한다. 프로젝트 루트는 한 단계만 감시해, 그 폴더가 나중에 생기는 것과 `README.md`가 바뀌는 것을 알아챈다.
- 변경이 몰려도 100ms 동안 모아 `changed` 이벤트 하나를 보낸다.
- 화면은 이벤트를 받으면 프로젝트와 열려 있는 문서를 다시 가져온다. 연결이 다시 열렸을 때도 그렇게 한다.
- 늦게 도착한 옛 응답은 버린다. 마지막에 보낸 요청의 응답만 화면에 반영한다(`web/live.ts`의 `latestOnly`).
- 감시할 수 없는 폴더가 있으면 그 폴더만 실시간 갱신 없이 보여 준다.

### 캐시

| 캐시 | 열쇠 | 한도 |
|---|---|---|
| 스캔이 파일 하나에서 계산한 값 | 프로젝트 경로, 파일 경로, 내용 해시 | 5000개 |
| `/api/doc`가 보내는 JSON | 프로젝트 경로, 파일 경로, 내용 해시 | 글자 수 합계 약 64 MB |
| 마크다운 파싱 결과 | 같은 글 | 직전 것 하나 |

한도를 넘으면 가장 오래 쓰지 않은 것부터 내보낸다(`server/cache.ts`). 내용 해시는 SHA-1의 앞 12자리다. 스캔할 때마다 파일을 읽고 해시를 계산하는 일은 그대로 하고, 내용이 바뀐 파일만 다시 파싱한다. 65,536자를 넘는 문서는 제목 줄에서 잘라 조각별로 파싱한다.

## 화면 주소

주소는 해시(`#`)에 둔다(`web/route.ts`).

| 주소 | 화면 |
|---|---|
| `#/` | 보드 |
| `#/stage/<단계>` | 그 단계의 문서. 기능은 현재 기능에 그 문서가 있으면 현재 기능, 아니면 그 문서가 있는 기능 가운데 가장 앞선 기능 |
| `#/stage/<단계>/<기능>` | 그 기능의 그 단계 문서 |
| `#/stage/plan/<기능>/<딸린 문서>` | 계획 단계의 딸린 문서. `research`, `data-model`, `quickstart`, `contract`. OpenSpec의 제안 단계는 `#/stage/propose/<변경>/delta`로 델타 스펙을 연다 |
| `#/doc/<경로>` | 경로로 연 문서 하나. 단계 페이지가 없는 문서(`other`, 두 번째 이후의 체크리스트와 계약 파일)에 쓴다 |

읽을 수 없는 주소는 보드로 간다. 주소에 적힌 기능이 없으면 다른 기능으로 바꾸지 않고 "더 이상 없다"고 알린다.

## 보드

첫 화면이다. 위에 프로젝트 띠가 있고, 아래에 단계 카드 여섯 장이 순서대로 놓인다(`web/Strip.tsx`, `web/Board.tsx`).

### 프로젝트 띠

| 자리 | 내용 |
|---|---|
| 이름 | 프로젝트 폴더 이름. 누르면 보드로 간다 |
| 소개 | `README.md`의 첫 글 문단 |
| 숫자 | 단계 수(6), 전체 작업 진행률과 끝난 수 / 전체, 끝난 기능 수 / 전체 |
| 다음 명령 | 대표 기능의 다음 명령과 복사 버튼, 그 이유 |
| 언어 | 한국어 / EN 전환 |

대표 기능은 끝나지 않은 현재 기능, 없으면 작업이 진행 중인 기능, 그것도 없으면 가장 앞선 미완료 기능이다.

### 단계 카드

| 자리 | 내용 |
|---|---|
| 머리 | 단계 번호와 이름(누르면 그 단계의 문서로), 그 단계의 명령 |
| 숫자 | 여기 있는 기능 수와 지나간 기능 수. 헌법 카드는 원칙 수와 기능 수 |
| 기능 | 여기 서 있는 기능의 링크. 9개부터는 접어 두고 "더 보기"로 편다. 기능이 둘 이하면 작업 진행 막대도 그린다 |
| 문서 | 이 단계가 남기는 문서 종류별 개수. 읽지 못한 문서 수도 적는다 |
| 다음 명령 | 여기 있는 기능에 입력할 명령과 복사 버튼, 그 이유 |

헌법 카드는 기능 대신 원칙 제목 목록과 헌법 버전을 보여 준다. 끝나지 않은 작업이 있는 기능이 서 있는 카드는 "진행 중"이라고 적고 초록색으로 그린다.

## 단계 문서 페이지

카드나 기능을 누르면 그 단계의 문서 페이지로 들어간다(`web/StagePage.tsx`, 문서 종류별 화면은 `web/forms/`).

### 공통 틀

| 자리 | 내용 |
|---|---|
| 위쪽 막대 | 보드로 돌아가기, 여섯 단계 칸, 기능 선택, 이전·다음 단계 |
| 차례 | 왼쪽에 고정된 구획 차례. 읽고 있는 구획을 따라 표시가 움직인다 |
| 머리 | 단계 번호와 이름, 문서 제목, 이 단계의 명령, 기능의 현재 단계와 다음 명령, 문서의 머리 정보, 기능의 문서 목록 |
| 본문 | 문서 종류별 화면 |
| 아래 | 이전 단계, 전체 보드, 다음 단계 |

계획 단계(OpenSpec은 제안 단계)에는 대표 문서와 딸린 문서를 오가는 탭이 있다. 같은 종류의 문서가 여럿이면(체크리스트, 계약 파일) 본문 위에서 고른다. `Esc`를 누르면 보드로 돌아간다.

### 단계별로 그리는 것

| 단계 | 문서 | 그리는 것 |
|---|---|---|
| 1 헌법 | `constitution.md` | 원칙 수, 버전, 제정일, 개정일. 번호가 붙은 원칙 판. 구획별 항목표 |
| 2 명세 | `spec.md` | 스토리·시나리오·요구사항·성공 기준·열린 질문 수. 스토리마다 우선순위와 서술, 시나리오별 Given → When → Then. 요구사항 묶음과 개수 막대. 성공 기준 |
| 3 계획 | `plan.md` | 요약, 기술 맥락 항목표, 헌법 점검, 프로젝트 구조 |
| | `research.md` | 결정마다 결정과 근거, 그 옆에 기각된 대안 |
| | `data-model.md` | 엔티티 카드, 관계 |
| | `quickstart.md` | 구획을 번호가 붙은 단계로 |
| | `contracts/*` | `.md`는 구획별 마크다운, 그 밖은 코드 보기 |
| 4 작업 분해 | `tasks.md` | 구조. 단계별로 작업 하나에 표시 하나, 병렬 작업은 한 열에, 스토리 꼬리표 |
| 5 구현 | `tasks.md` | 진행. 끝난 수 / 전체, 모든 작업의 칸, 단계별·스토리별로 남은 것, 다음 명령 |
| 6 완료 | `checklists/*.md` | 확인한 수 / 전체, 묶음별 항목 |

각 화면이 어느 블록에서 무엇을 그리는지는 [parsing-rules.md](parsing-rules.md)에 있다.

## 안내 규칙

화면은 명령을 실행하지 않는다. 다음에 입력할 명령을 보여 주고 복사하게 한다(`web/guide.ts`).

### 기능 하나의 다음 명령

| 기능의 단계 | 다음 명령 |
|---|---|
| 명세, 열린 질문 있음 | `/speckit.clarify` |
| 명세, 열린 질문 없음 | `/speckit.plan` |
| 계획 | `/speckit.tasks` |
| 작업 분해, 구현 | `/speckit.implement` (남은 작업 수와 함께) |
| 완료 | 없음 |

### clarify 규칙

`/speckit.clarify`는 여섯 단계에 들어 있지 않다. 명세 단계에 있는 기능에 열린 질문(`NEEDS CLARIFICATION`)이 하나라도 있을 때만 다음 명령으로 나온다. 명세 단계 카드에서는 다음과 같이 쓴다.

| 명세 단계에 있는 기능 | 카드의 명령 |
|---|---|
| 모두 열린 질문이 있음 | `/speckit.clarify` |
| 일부만 열린 질문이 있음 | `/speckit.plan`. 몇 개는 `/speckit.clarify`가 먼저라고 덧붙인다 |
| 열린 질문 없음 | `/speckit.plan` |

### 카드의 다음 명령

| 카드 | 명령 |
|---|---|
| 헌법 | 헌법이 없으면 `/speckit.constitution`, 있으면 `/speckit.specify` |
| 명세, 계획, 작업 분해 | 다음 단계로 넘기는 명령 (`/speckit.plan`, `/speckit.tasks`, `/speckit.implement`) |
| 구현 | `/speckit.implement`와 남은 작업 수 |
| 완료 | `/speckit.specify` (새 기능을 시작) |

기능이 서 있지 않은 명세, 계획, 작업 분해, 구현 카드는 같은 명령을 흐리게 보여 준다.

### 프로젝트 띠의 다음 명령

| 상황 | 명령 |
|---|---|
| 대표 기능이 있음 | 그 기능의 다음 명령 |
| 모든 기능이 끝남 | `/speckit.specify` |
| 기능이 없고 헌법이 있음 | `/speckit.specify` |
| 기능도 헌법도 없음 | `/speckit.constitution` |

### 문서가 없을 때

기능이 아직 그 단계에 이르지 않아 문서가 없으면, 페이지는 기능이 지금 어느 단계에 있는지, 어떤 문서가 없는지, 지금 입력할 명령과 그 문서를 만드는 명령을 알려 준다. 체크리스트를 만드는 명령은 안내하지 않는다.

## 상태

| 상태 | 언제 | 화면 |
|---|---|---|
| 불러오는 중 | 첫 화면이 준비되기 전 | 요청한 화면 모양의 뼈대. 보드는 카드 여섯 장의 윤곽 |
| 다음 화면을 기다리는 중 | 다른 주소로 가는 동안 | 지금 화면을 그대로 두고 위에 진행 줄만 보인다 |
| 빈 프로젝트 | 기능이 없음 | 보드에 첫 명세를 쓰는 명령을 적는다. 단계 페이지도 같은 명령을 안내한다 |
| 문서가 아직 없음 | 기능이 그 단계에 이르지 않음 | [문서가 없을 때](#문서가-없을-때)의 안내 |
| 완료, 체크리스트 없음 | 끝난 기능에 체크리스트가 없음 | 완료되었고 입력할 명령이 없다고 알린다 |
| 읽기 오류 | 스캔이 파일을 읽지 못함 | 그 문서만 오류로 표시하고 경로와 오류 글을 보여 준다. 나머지는 정상이다 |
| 사라짐 | 열려 있던 문서나 주소의 기능이 지워짐 | 더 이상 없다고 알린다 |
| 새로 읽기 실패 | 열린 문서를 다시 가져오지 못함 | 마지막으로 읽은 내용을 두고 그 사실을 알린다 |
| 그리기 오류 | 화면을 그리다 예외가 남 | 그 화면 자리에 오류를 알린다. 주소나 데이터가 바뀌면 다시 그린다 |
| 연결 끊김 | 서버와의 SSE 연결이 끊김 | 끊겼다고 알리는 띠. 브라우저가 다시 연결하면 사라진다 |

## 새 문서와 갱신 표시

- 브라우저의 localStorage에 문서별 "마지막으로 열었을 때의 내용 해시"를 프로젝트 절대 경로별로 저장한다(`web/seen.ts`).
- 기록에 없는 문서는 "새 문서", 저장한 해시와 지금 해시가 다른 문서는 "갱신"이다. 문서를 열면 표시가 사라진다.
- 프로젝트를 이 브라우저에서 처음 열 때는 그 시점의 문서를 모두 본 것으로 기록한다. 그러지 않으면 모든 문서에 "새 문서"가 붙는다.
- 파일 수정 시각은 쓰지 않는다. 브랜치를 바꾸면 내용이 같아도 시각이 바뀌기 때문이다.
- 읽기 오류가 난 문서에는 표시를 달지 않는다.
- 저장소를 쓸 수 없으면 표시가 초기화될 뿐 화면은 그대로 동작한다.

## 언어와 테마

| 항목 | 규칙 |
|---|---|
| 언어 | 한국어와 영어. 화면의 라벨만 바뀌고, 문서에서 읽은 글은 원문 그대로다 |
| 처음 언어 | 브라우저 언어가 한국어면 한국어, 아니면 영어 |
| 전환 | 프로젝트 띠 오른쪽의 버튼. 고른 언어는 localStorage에 저장한다 |
| 라벨 | `web/i18n.ts`의 표 하나. 두 언어의 열쇠가 같은지 타입 검사로 확인한다 |
| 테마 | 시스템의 밝은 / 어두운 설정을 따른다. 화면에 전환 버튼은 없다 |
| 글꼴 | 시스템 글꼴만 쓴다. 외부에서 받아 오는 것이 없다 |
| 움직임 | 시스템에서 움직임 줄이기를 켜면 카메라 이동과 미끄러짐을 하지 않는다 |

## 내용을 버리지 않는 규칙

문서에 있는 글은 어떤 경우에도 화면 어딘가에 나와야 한다. 세 곳에서 지킨다.

| 곳 | 방법 |
|---|---|
| 파서 | 규칙에 맞지 않는 구획은 `raw` 블록으로, 구획 안에서 맞지 않는 부분은 `rest`로 원문을 남긴다. 파서가 실패하면 문서 전체를 `raw` 블록 하나로 준다 |
| 문서 화면 | 화면은 자기가 그린 블록을 알려 준다. 그리지 않은 블록은 문서 끝의 "원문 블록 더 있음" 아래에 모두 나온다 |
| 틀을 벗어난 문서 | 기대한 구조가 하나도 없으면 원문의 구획 순서대로 그린다 |

예외는 HTML 주석 하나다. spec-kit 템플릿의 작성 지침이 주석으로 남기 때문에 숨긴다. 테스트(`test/forms.test.ts`)는 문서의 조각마다 고유한 낱말을 넣고, 파싱해서 그린 화면에 그 낱말이 모두 있는지 문서 종류별로 확인한다.

## 나타난 뒤에는 움직이지 않는 규칙

화면에 한 번 나타난 것은 뒤늦게 도착한 데이터 때문에 자리를 옮기지 않는다.

| 규칙 | 방법 |
|---|---|
| 화면을 통째로 한 번에 바꾼다 | 주소가 바뀌어도 프로젝트와 문서가 모두 도착할 때까지 지금 화면을 둔다. 다 오면 한 번에 바꾼다(`web/main.tsx`의 `view`). 페이지의 본문은 주소와 문서별로 새로 그린다 |
| 차례 칸을 비워 두지 않는다 | 차례 상자는 구획이 없어도 같은 자리에 있고, 없다는 한 줄을 적는다 |
| 프로젝트 띠의 높이를 고정한다 | 불러오는 중이든 빈 프로젝트든 높이와 칸이 같다 |
| 뼈대가 실제 화면과 같은 모양이다 | 첫 화면 전의 뼈대는 실제 막대, 차례 칸, 머리, 본문과 같은 자리를 차지한다 |
| 읽던 자리를 지킨다 | 방문 기록 항목마다 스크롤 위치를 sessionStorage에 저장한다. 뒤로, 앞으로, 새로 고침은 읽던 자리로 돌아가고, 새 항목은 맨 위에서 시작한다(`web/scroll.ts`) |
| 탭 줄을 지킨다 | 계획 탭이나 문서 고르기 버튼을 누르면 그 줄이 화면에서 같은 높이에 남는다 |

보드에서 문서로 들어갈 때는 누른 카드가 화면 전체로 커지는 카메라 이동을 쓰고, 단계 사이를 옮길 때는 옆에서 미끄러져 들어온다(`web/camera.ts`). 둘 다 `transform`과 `opacity`만 움직인다. 폭이 1000px 이하인 화면에서는 차례가 본문 위의 가로 줄로 바뀐다.

## 보안 경계

도구는 자기 컴퓨터에서 자기 프로젝트를 보는 용도다. 문서의 글은 신뢰하지 않는다.

| 경계 | 방법 |
|---|---|
| 읽기 전용 | 프로젝트 폴더에 쓰는 코드가 없다. 서버는 `GET`만 받고 나머지는 405로 답한다 |
| 로컬 전용 | `127.0.0.1`에만 연결을 받는다 |
| Host 확인 | `Host`가 `127.0.0.1:<포트>`나 `localhost:<포트>`가 아니면 403으로 답한다 |
| 문서 접근 | `/api/doc`는 스캔이 찾은 문서의 경로만 받는다. 임의의 경로는 404다 |
| 심볼릭 링크 | 스캔과 형식 찾기는 심볼릭 링크를 따라가지 않는다. `specs`, `.specify`, `memory`, `openspec`, `.kiro`가 링크여도, README가 링크여도 읽지 않는다 |
| 화면 파일 | 실제 경로가 화면 폴더 안에 있는 파일만 준다 |
| 응답 머리 | 모든 응답에 `Cache-Control: no-store`와 `X-Content-Type-Options: nosniff`를 붙인다 |
| 원시 HTML | 마크다운 안의 HTML은 실행하지 않고 글자로 보여 준다 |
| 링크 | `http:`, `https:`, `#`으로 시작하는 링크만 따라갈 수 있고 새 탭에서 열린다. 나머지는 글자와 주소로 보여 준다 |
| 이미지 | 불러오지 않는다. 대체 글과 주소를 글자로 보여 준다 |
| 브라우저 열기 | 주소를 인자 하나로 넘겨 여는 명령을 실행한다. 셸을 거치지 않는다 |

## 전달

### npm 패키지

```sh
npx spec-visualizer            # 현재 폴더의 spec-kit 프로젝트
npx spec-visualizer --demo     # 함께 들어 있는 예제 프로젝트
```

| 패키지에 들어가는 것 | 내용 |
|---|---|
| `dist/server` | JavaScript로 빌드한 서버. 실행 파일은 `dist/server/cli.js` |
| `dist/web` | 빌드한 화면 파일. React는 여기에 묶여 들어간다 |
| `examples/demo`, `examples/demo-openspec`, `examples/demo-kiro` | `--demo`가 보여 주는 예제 프로젝트. 뒤의 둘은 `--format openspec`, `--format kiro`와 함께 쓴다 |
| `package.json`, `README.md`, `LICENSE` | npm이 항상 넣는 파일 |

실행할 때 필요한 의존성은 마크다운 파서(`unified`, `remark-parse`, `remark-gfm`)뿐이다. 패키지는 Node.js 20 이상에서 실행한다. `docs/`와 테스트는 패키지에 들어가지 않는다.

### CLI

```text
spec-visualizer [path] [options]
```

| 인자 | 동작 |
|---|---|
| `path` | 보여 줄 프로젝트. 생략하면 현재 폴더. 어느 형식의 폴더도 없으면 알리고 끝낸다 |
| `--format <이름>` | `spec-kit`, `openspec`, `kiro` 가운데 하나로 읽는다. 폴더가 그 형식에 맞지 않으면 알리고 끝낸다 |
| `--port <n>` | 들을 포트. 기본값은 4321 |
| `--demo` | 경로 대신 예제 프로젝트를 보여 준다. 경로와 함께 쓸 수 없다. `--format`과 함께 쓰면 그 형식의 예제 |
| `--no-open` | 브라우저를 열지 않는다 |
| `--help`, `--version` | 사용법이나 버전을 출력한다 |

- `--port`를 주지 않았을 때 4321이 사용 중이면 4330까지 차례로 시도한다. `--port`로 준 포트가 사용 중이면 오류로 끝낸다.
- 시작하면 기능 수와 문서 수, 주소를 출력한다.
- 브라우저는 출력이 터미널일 때만 연다. 파이프, 스크립트, 에이전트가 실행하면 열지 않는다.

### Claude Code 플러그인

`plugin/`에 플러그인이 있고, `.claude-plugin/marketplace.json`이 이 저장소를 그 플러그인의 마켓플레이스로 만든다. 플러그인은 `dashboard` 스킬 하나다. 스킬은 `npx --yes spec-visualizer@latest --no-open`을 백그라운드로 실행해 출력된 주소를 사용자에게 알리고, 요청하면 열거나 멈춘다. 대시보드 자체는 npm 패키지와 같다.

### 예제 프로젝트

`examples/demo`는 가상의 제품 Borrowbox를 spec-kit으로 쓴 프로젝트다. 헌법 하나와 기능 일곱 개가 있고, 기능들이 다섯 단계에 고루 서 있어 모든 화면에 그릴 것이 있다. `examples/demo-openspec`과 `examples/demo-kiro`는 같은 제품을 OpenSpec과 Kiro로 쓴 것이고, 역시 모든 단계에 작업 단위가 있다.

## 알려진 한계

| 한계 | 설명 |
|---|---|
| 여러 조각에 걸쳐 열린 코드 블록 | 긴 문서를 조각으로 자를 때 코드 블록이 여러 자리에 걸쳐 열려 있으면 자리마다 한 번씩 다시 파싱한다. 결과는 같고 시간이 더 든다 (`server/md.ts`) |
| 이름표가 없는 Technical Context | 빈 항목표 대신 원문(`raw`)으로 남는다 (`server/parsers.ts`) |
| 포트가 바뀌면 표시가 초기화된다 | 새 문서·갱신 기록과 언어 선택은 브라우저가 주소(포트 포함)별로 저장한다. 다른 포트로 열면 처음 여는 것으로 본다 |
| 브라우저에서의 자동 테스트가 없다 | 테스트는 서버, 파서, 주소·안내·기록 규칙, 그리고 문서 화면을 글자로 그린 결과를 확인한다. spec-kit은 두 예제 프로젝트의 API JSON과 모든 화면의 HTML을 기준 파일과 비교한다(`test/speckit-golden.test.ts`). 보드, 프로젝트 띠, 단계 페이지의 틀, 카메라 이동, 포커스 이동, 스크롤 복원은 실제 브라우저에서 자동으로 확인하지 않는다 |

## 결정 기록

### 유지하는 결정

| 결정 | 내용 |
|---|---|
| 규칙 기반 로컬 웹앱 | 문서의 일정한 표식을 규칙으로 읽는다. 바로 뜨고 항상 최신이며 비용이 없다. AI가 문서마다 페이지를 만드는 방식과 에디터 확장은 택하지 않았다 |
| 파싱은 서버에서만 | 마크다운의 구조는 remark(mdast)로 읽는다. 화면은 문서 구조를 파싱하지 않는다 |
| 최신 상태만 보여 준다 | 갱신된 문서는 지금 내용을 보여 주고 표시만 단다 |
| 영어와 한국어 라벨 | 전환 버튼을 두고, 번역 라이브러리 없이 라벨 표 하나로 처리한다 |
| 열린 질문은 단계를 막지 않는다 | `plan.md`가 있으면 계획 단계다. 질문 수는 따로 보여 준다 |
| 현재 기능은 git 브랜치와 같은 이름의 폴더 | spec-kit이 기능마다 같은 이름의 브랜치를 만들기 때문이다 |
| 일부만 인식되면 | 아는 구획은 전용 화면으로, 나머지는 마크다운으로 보여 준다 |
| HTML 주석은 숨긴다 | 템플릿의 작성 지침이고 문서 내용이 아니다 |
| data-model은 엔티티 카드까지 | 관계 그래프는 그리지 않는다 |
| 모르는 이름의 `.md` | `other` 문서로 보여 준다 |
| 열린 페이지는 바로 갱신한다 | 파일이 바뀌면 새로 고침 없이 갱신하고 읽던 자리를 지킨다 |
| 열람 기록은 브라우저에 | 프로젝트 경로별로 저장하고, 처음 열 때는 표시가 없다 |
| 변경은 내용 해시로 판단한다 | 파일 수정 시각은 쓰지 않는다 |

### 바뀐 결정

| 처음 결정 | 지금 |
|---|---|
| 기능 목록이 중심인 홈 화면 | 단계 카드 여섯 장의 보드 |
| 문서 종류마다 문서 페이지 하나 | 단계마다 문서 페이지 하나. `tasks.md`는 작업 분해와 구현 두 단계에서 다르게 그린다 |
| 다섯 단계 (Specify부터 Done까지) | 헌법을 첫 단계로 둔 여섯 단계 |
| 홈에서 종류별 문서 수와 미해결 질문 수를 요약 | 카드마다 그 단계의 문서 수를 세고, 열린 질문은 명세 페이지와 다음 명령(`/speckit.clarify`)으로 보여 준다 |
| quickstart는 다듬은 마크다운 | 구획을 번호가 붙은 단계로 그린다 |
| 포트가 사용 중이면 알리고 멈춘다 | 기본 포트는 다음 빈 포트로 넘어간다. `--port`로 준 포트만 오류로 끝낸다 |
| 실행 인자는 경로와 `--port` | `--demo`, `--no-open`, `--help`, `--version`을 더했다 |
| npm 배포 여부는 정하지 않음 | npm 패키지와 Claude Code 플러그인으로 전달한다 |
| spec-kit 문서만 읽는다 | OpenSpec과 Kiro도 읽는다. 형식마다 어댑터와 화면 흐름이 있고, spec-kit의 출력은 그대로다([다른 형식](#다른-형식)) |
